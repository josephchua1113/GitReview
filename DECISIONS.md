# git_history.py: decisions the spec didn't cover

1. **Parsing.** `git log` runs with `-z` and NUL-separated fields. A NUL byte can't appear in a commit message, name, email or date, and `-z` stops git from quoting unusual paths (tabs, newlines, non-ASCII characters). The command also adds `--encoding=UTF-8 --no-color --no-show-signature --no-mailmap`, so user git config can't change the output. Output that doesn't parse becomes an error for that repository. Nothing is dropped silently.
2. **Remote-only refs.** Branches are listed with `%(refname)` instead of `%(refname:short)`. The short form turns into `remotes/origin/...` when a local branch has the same name, and that would silently hide the remote branch. `git log` also uses full `refs/remotes/...` names, so a local branch or tag with the same name is never read.
3. **Versions** are compared part by part as numbers. When the shared parts are equal, the version with more parts is higher, so `19.17` < `19.17.0` < `19.17.1`. With `hotfix/SG_19.17` and `release/SG_19.17.0` both present, the base is `release/SG_19.17.0`. When `release/` and `hotfix/` branches share the closest lower version (for example `release/SG_19.17.0` and `hotfix/SG_19.17.0`), the one `release/` branch is the base. The page lists the hotfix branch under "Same version as base" and tags it "not used". Any other same-version tie, such as two `hotfix/` branches like `19.17.0` and `19.017.0`, or two `release/` branches, is still an error. Leading zeros don't count (`19.017.0` = `19.17.0`). As a consequence, for target `19.18.0` a branch `19.18` counts as lower and can become the base. Country is ASCII letters only and is case-sensitive. Version is ASCII digits and dots.
4. **Error vs. No change.** Fetch failure, no lower branch, a tie and parse or git failures go in the red **Errors** group at the top. A missing target branch and an empty `base..target` go in the **No change** group. Within each group, repositories are sorted alphabetically, ignoring case. Files are sorted the same way.
5. **Renames and copies** are listed under the new path. The entry shows `old → new` and the score, for example `R087`. Searching the old path also finds the entry.
6. **Author email** (`%ae`) is shown next to the name and is searchable. It is left out when it is empty.
7. **Commit messages.** Only the trailing newline that git adds is removed. Everything else is shown unchanged.
8. **DIFF_URL_TEMPLATE** is `{"commit": ..., "compare": ...}` (a 2-tuple also works). It is checked at startup: only known placeholders are allowed, and it must start with `{base_url}` or `http(s)://`. `{path_sha1}` was added for self-hosted GitLab anchors. The template is used only for hosts that aren't recognised. Branch names are encoded with `/` as `%2F`. Paths keep `/`.
9. **Remote URLs.** Credentials in https URLs are removed, and ssh ports are dropped. Azure's `git@ssh.dev.azure.com:v3/org/proj/repo` becomes `https://dev.azure.com/org/proj/_git/repo`. Older `*.visualstudio.com` Azure URLs aren't recognised and need the template. Local paths and `file://` remotes give no links.
10. **Links not narrowed to the file.** Azure DevOps commit and compare links open the whole commit or compare page, because no file parameter or anchor could be confirmed. Bitbucket's `source%0Ddestination` order and its `#chg-<path>` anchor come from Bitbucket's UI behaviour, not from written documentation. Check one generated Bitbucket link before relying on it.
11. **Filters and print.** Search and the status filter hide only individual entries. Error and No change repositories are never hidden. A banner says when a filter is active, and a repository whose entries are all filtered out shows a "no entries match" line. Printing expands every section and ignores filters, so the printout is always complete. Merge commits without files have their own status checkbox, "Commits with no file changes".
12. **Inputs and environment.** `REMOTE_NAME` may not contain `/`, because the `<remote>/` prefix must be unambiguous. git runs with `GIT_TERMINAL_PROMPT=0`, so a fetch never waits for a password, and inherited `GIT_DIR` and `GIT_WORK_TREE` are removed. There is no fetch timeout.
13. **Layout.** Each repository shows a two-column table. Column 1 is the file path, with its Compare link and anchor, and stays visible while you scroll that file's commits. Column 2 holds the changes: status badge, message, date, commit id and user. Column 2 can be collapsed for one file (its "Changes" toggle) or for every file at once ("Hide changes column" in the toolbar), which leaves a compact list of files. Everything is open by default. On narrow screens the columns stack. Printing always includes both columns.
14. **BITBUCKET_BASE_URL** is a new setting in the configuration block, for example `"https://bitbucket.mycompany.com"`. When it is set, every repository's links are built from it. The project (or workspace) and repository name come from each repo's remote URL: the last two parts of its path, after `scm/` if there is one. A path with `~user` gives a personal-repository link. `https://bitbucket.org` uses Bitbucket Cloud link formats. Any other address uses Bitbucket Server / Data Center formats under `<base>/projects/<KEY>/repos/<repo>`:
    - commit diff: `/commits/<sha>#<path>`
    - compare diff: `/compare/diff?sourceBranch=refs/heads/<target>&targetBranch=refs/heads/<base>#<path>`. The source is the target release and the target is the base.
    - file: `/browse/<path>?at=<target commit>`

    Only the file format is confirmed by Atlassian's API docs. The commit and compare formats are the ones Bitbucket Server's own pages use, but Atlassian doesn't document them, so click one of each on your server. Setting BITBUCKET_BASE_URL together with DIFF_URL_TEMPLATE is a configuration error.
15. **File links.** Each file in column 1 now has a **File ↗** link, on every platform. It opens the file as it is at the target branch's current commit, read with `git rev-parse`. It appears only when the file exists in that commit (checked with `git ls-tree`), so deleted files have no file link. DIFF_URL_TEMPLATE accepts an optional `"file"` template with a new `{target_commit}` placeholder.
16. **FALLBACK_BASE_BRANCH** is a new setting, `"master"` by default. If the target branch exists but no `release/` or `hotfix/` branch of the same country has a lower version, the base becomes `<REMOTE_NAME>/master`. This is a change you asked for: the original spec allowed no fallback. Repositories that use the fallback get a "fallback base" tag in the overview and in the repository header, plus a "Fallback base" line explaining why. If `origin/master` doesn't exist either, the repository shows "No previous branch found…" and the message says the fallback branch was not found. The fallback is never used when the target is missing or when there is a tie. Set it to `None` to turn the fallback off, or to another name such as `"main"`.
17. **Code diff column.** A new collapsible column sits between the file name and the commits column. It shows that file's part of `git diff <base>...<target>`: what the target changed since it branched from the base, the same scope as the commit list. One `git diff` runs per repository rather than one per file. `--name-status -z` names the files exactly, and the patch is split at each `diff --git` line. Generating a 244-file release went from 5.7 s to 0.3 s. Renames are detected across the whole range, and both the old and new path rows show the rename. Only the code changes are shown. git's per-file header (`diff --git`, `index`, `---`, `+++`, mode lines) is left out. Every line from the first `@@` hunk header on is kept unchanged and colored by type: added, removed or hunk header. A file with no hunks, such as a pure rename or a binary file, keeps its descriptive header lines (for example `rename from a.txt` or `Binary files … differ`), because otherwise its cell would be empty. Long diffs scroll inside a box with a 600 px maximum height, and printing shows them in full. You can collapse the column for one file, or for every file with "Hide code diff column". If the diff fails, the code diff cells show the error and the commit list is still shown. File names that aren't valid UTF-8 now get their diff too. Search doesn't look inside diff text.
18. **Statistics page** (`STATS_OUTPUT_FILE = "stats.html"`; set it to `None` to skip it). This is a separate page, written next to the review page, and the two pages link to each other. The original "no counts or categories" rule still covers the review page; this page exists because you asked for counts and categories. For each repository with changes, it lists every file in the same `base..target` scope with:
    - **Commits:** how many commits changed the file. This matches the number listed under the file on the review page.
    - **Users:** how many different author names made those commits. Hovering shows the names.
    - **Commit messages:** a collapsible list (closed by default) with each commit's full message, status, date, id and author.

    The file name links to that file on the review page. Merge commits that change no file aren't counted. Error and No change repositories are listed at the top with their reason.

    **Type groups** come from the file name only, never its folder or content. They appear in your order: Controller, Processor, Route, Config, API, Builder, Mapper, VO, Request, Response, Test, then Other. The name without its extension is split into words at `.`, `_`, `-` and camelCase, keeping acronyms such as `VO` and `API` together.
    - **Test:** the name starts with `test` or ends with `Test`, `Tests`, `Spec` or `IT`. For example `UserControllerTest.java`, `test_api.py`, `user.spec.ts` and `UserServiceIT.java`.
    - **Every other type:** the last word that names a type decides. `OrderRequestMapper.java` is a Mapper. Plurals and close forms count too: `routes`/`router` are Route, `configuration` is Config.
    - **Other:** files with no such word, for example `README.md` or `pom.xml`.
19. **More stats groups and the multi-user summary.**
    - **New name-based groups:** Properties (`.properties` files, or `properties`/`props` in the name), Util (`util`, `utils`, `utility`) and Constant (`constant`, `constants`, `const`).
    - **Folder groups apply only when the name matches no type.** A file inside a `resources/`, `routes/` or `template(s)/` folder at any depth goes to Resources, Route or Template. The innermost such folder decides. The file's name still takes priority: `resources/UserMapper.xml` stays a Mapper and `resources/application.properties` is Properties. Files in a `routes/` folder join the existing Route group rather than a separate one.
    - **Group order:** your original list, then Properties, Util, Constant, Resources, Template, then Other.
    - **Summary at the top:** for each repository, a table of the files changed by more than one user, with the file's type, user count, commit count and user names. It's sorted by user count, most first. Each file links to its row further down the page. A repository with no such file says so.
